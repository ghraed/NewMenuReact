MARKET READINESS REVIEW — 7 OCTOBER 2026
Projects: Menu_React and Menu_API
Decision: Neither project is ready for an unrestricted commercial launch.
Menu_React readiness: 6.0/10. Menu_API readiness: 6.5/10.
These are engineering judgments of readiness, not measured coverage percentages,
legal certifications, or a review of a live deployment. The scores reflect substantial
working functionality and passing regression suites, reduced by reproduced financial
and browser tenant-isolation defects and incomplete deployment assurance.

URGENT — FIX OR CLOSE BEFORE COMMERCIAL LAUNCH

U1. P0 — POS compensation shown in the UI is ignored during checkout.
  Projects/roles: both; admin/cashier and customers receiving complimentary items.
  Reproduce:
    1. Enable table_ordering; log in as a tenant admin with a published $10 packaged
       item and sufficient stock.
    2. Open /staff/pos; choose Complimentary for that item.
    3. Open Edit Issue / Compensation, then Save Compensation.
    4. Observe displayed Total $0.00; press Checkout (Ctrl+Enter).
    5. Inspect POST /api/pos/checkout response/order invoice.
  Expected: supported approved compensation persists and payable invoice total is
    $0.00; an unsupported adjustment must be rejected clearly before settlement.
  Actual: HTTP 201, invoice total "10.00" while the UI had shown $0.00.
    Core sale is recorded at the full catalog price. No live payment was made.
  Errors: no browser page error; the request incorrectly succeeds.
  Determinism: reproduced in the successful final browser run; repeated checkout
    probing also confirmed the behavior. Root cause is deterministic field omission.
  Likely modules: Menu_React/src/pages/CashierPosPage.tsx (checkout payload),
    Menu_API/app/Http/Controllers/OrderController.php:1452 (quickCheckout validates
    only base item fields and calls prepareOrderItems/server pricing).
  Evidence: compensation-checkout-evidence.json, browser-reproductions.json,
    compensation-double-count.png (completed sale and dashboard state).
  Tests to add: approved complimentary, full waiver, partial discount and cancelled
    line checkout; server-side approver authorization; receipt/UI/finance/stock parity.

U2. P0 — multiple refunds can exceed the original sale value.
  Project/roles: Menu_API; admin/accountant, cashier and finance users.
  Reproduce:
    1. Complete one $10 POS sale and take its order/item IDs.
    2. POST /api/pos/orders/{order}/complaint-adjustments with a valid affected
       item, QA complaint reason and refund_amount=8; POST the returned adjustment
       to /api/pos/complaint-adjustments/{adjustment}/post.
    3. Repeat with a new adjustment for the same sale and refund_amount=8.
    4. GET /api/admin/finance/profit-loss?date_from=2026-10-07&date_to=2026-10-07.
  Expected: aggregate posted refunds never exceed refundable balance; second
    posting is rejected without financial/stock side effects.
  Actual: both creates return 201 and both postings 200. For the isolated tenant,
    complaint_refunds=16 and revenue/net_profit=-6 on the original $10 sale.
  Errors: none; requests succeed incorrectly. No live payout was made.
  Determinism: reproduced for two independent synthetic tenants.
  Likely modules: PosComplaintAdjustmentController.php:40/83,
    InvoiceController.php:353/763. Only each individual refund is capped.
  Evidence: api-reproductions.txt; synthetic order 3 / adjustment IDs 3 and 4.
  Tests to add: cumulative refunds, concurrent approvals, stale draft revalidation,
    request retries, posting idempotency, post/void races, and tenant/role denial.

U3. P0 — compensation data survives tenant logout/login on a shared browser origin.
  Project/roles: Menu_React; restaurant A/B admins and staff named in reports.
  Reproduce:
    1. At the same frontend origin, log in as restaurant A's admin.
    2. Record a complimentary item through /staff/pos as above.
    3. Use the application's logout flow, then log in as restaurant B's admin.
    4. Open /staff/pos and inspect Complaint & Compensation Dashboard.
  Expected: B's report contains only B's data, using tenant-scoped storage or an
    authorized server report; logout invalidates sensitive account-local state.
  Actual: B sees A's $20 compensation total and QA_RUN_20261007_a_admin name.
    Both login/me and A logout responses return 200. B's catalog requests use B's
    slug, so this is browser-retained data rather than a demonstrated API row leak.
  Scope: reproduced when accounts share an origin/browser profile. Separate custom
    domain origins isolate browser storage, but do not fix the shared-origin case.
  Errors: no browser page errors. Determinism: deterministic retained storage.
  Likely modules: src/services/complaintCompensationService.ts:71/96/112,
    src/pages/CashierPosPage.tsx:308, src/contexts/AuthContext.tsx (logout).
  Evidence: browser-reproductions.json and compensation-other-tenant.png.
  Tests to add: A -> logout -> B, different roles, fresh browser/server consistency,
    and tenant scoping for compensation/held orders/other persisted business state.

U4. P2 — compensation dashboard counts one item twice, including provisional edits.
  Project/roles: Menu_React; admin/cashier and report readers.
  Reproduce: save compensation for one $10 item in /staff/pos; observe $10 report
    total; check out that same item; refresh the report.
  Expected: one final $10 compensation contributes once; edits remain audit events.
  Actual: Total Compensation Cost and Complimentary Value become $20, with two
    approvals. Ledger contains marked_complimentary and checkout entries for the
    same item, each with loss_amount=10. Checkout returns 201, no console error.
  Determinism: deterministic aggregation. Likely modules: CashierPosPage.tsx:582/644
    and complaintCompensationService.ts:167 (sums every event without finalization).
  Evidence: browser-reproductions.json, compensation-double-count.png.
  Tests to add: edit/save/checkout produces one financial entry; repeated edits,
    removing a draft, returning to normal, failed checkout, and fresh browser reports.

U5. P2 — restaurant activation status currently does not stop operations.
  Project/roles: Menu_API; super admin and inactive restaurant admin/guests.
  Reproduce: set a synthetic restaurant to status=inactive, leave its core flags
    enabled and its admin user active. Log in; create a published packaged dish;
    GET /api/menu/{inactive-slug}/dishes; POST /api/pos/checkout.
  Expected launch policy: an inactive restaurant cannot accept sales. If status is
    intended as an informational field, document that explicitly and provide a
    separate reliable suspension mechanism.
  Actual: login=200, dish creation=201, public menu=200 with one dish, sale=201.
    Feature flags and user activity are enabled and routes are registered; this is
    not a missing page caused by a disabled plan/flag. No subscription-plan model
    enforcing suspension was found. No server exception.
  Determinism: deterministic. Likely modules: AuthController.php,
    TenantRestaurantResolver.php, EnsureActiveUser.php, EnsureRestaurantFeatureEnabled.php,
    SuperAdminRestaurantManagementController.php (status mutation).
  Evidence: api-reproductions.txt (inactive_restaurant_enforcement).
  Tests to add: inactive tenant guest/staff/finance access and existing token behavior,
    reactivation, enabled/disabled flags independent of status.

  sequential requests; it is not simultaneous contention. InventoryConcurrencyTest
  tests a held ingredient lock, which is useful but not a complete overselling test.

  finalization and idempotency tests across real workers/connections.

  the first owned/staff restaurant. No explicit tenant selection/membership test found

  config blocks service workers; unit mocks cannot prove caching, reconnect, closed
  sessions, multi-tab replay, lost acknowledgments or upgrade recovery in real browsers.

  focus management, room-plan dragging alternatives, form errors, Arabic/RTL and print.
N5. Replace framework-template READMEs with product setup/deployment/operations docs:
  supported feature combinations, role permissions, test DB setup, worker/scheduler
  requirements, browser/PDF dependencies, backup restoration, rollback and monitoring.

  exist; a standalone automated subscription/plan billing implementation was not
